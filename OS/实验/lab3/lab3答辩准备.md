### 1. RISC-V中断与异常的区别，是否都可以恢复？

在RISC-V架构中，**中断（Interrupt）** 和 **异常（Exception）** 都被统称为 **陷阱（Trap）**。它们都会打断处理器当前的执行流程，转而去执行一个预设的陷阱处理程序。但它们的区别主要在于来源和同步性：

*   **异常 (Exception)**：
    *   **来源**：由处理器内部执行指令时产生，是**同步**事件。也就是说，异常的发生与特定的指令执行直接相关。
    *   **例子**：执行一条非法指令、访问无效的内存地址（缺页）、除以零、或者主动执行 `ecall`（系统调用）或 `ebreak`（断点）指令。
    *   **可恢复性**：**不一定都能恢复**。
        *   **可恢复的**：例如“缺页异常”。操作系统可以加载所需页面到内存中，然后重新执行导致异常的指令，程序可以继续正常运行。
        *   **不可恢复的**：例如“执行非法指令”或“除零”。这种通常是程序错误，操作系统无法修复，一般的处理方式是终止该程序。

*   **中断 (Interrupt)**：
    *   **来源**：由处理器外部的硬件设备产生，是**异步**事件。也就是说，中断的发生与当前正在执行的指令无关，它可能在任何时候到来。
    *   **例子**：时钟芯片发出的定时器中断、网卡收到数据包、键盘被按下。
    *   **可恢复性**：**通常是可恢复的**。中断处理程序（ISR）服务完外部设备后，被中断的程序应该能从它被打断的地方无缝地继续执行，就好像什么都没发生过一样。

### 2. ucore区分中断和异常的地方

在实验指导书的代码中，ucore 通过检查 `scause`（Supervisor Cause Register）寄存器的值来区分中断和异常。`scause` 记录了陷阱发生的原因。

RISC-V 规范规定，`scause` 寄存器的最高位（Most Significant Bit, MSB）用于区分中断和异常：
*   **如果最高位是 1**，表示这是一个**中断**。
*   **如果最高位是 0**，表示这是一个**异常**。

在 `kern/trap/trap.c` 的 `trap_dispatch` 函数中，可以看到这个判断逻辑：

```c
static inline void trap_dispatch(struct trapframe *tf) {
    // scause的最高位是1，说明trap是由中断引起的
    if ((intptr_t)tf->cause < 0) {
        // interrupts
        interrupt_handler(tf);
    } else {
        // exceptions
        exception_handler(tf);
    }
}
```

这里的 `(intptr_t)tf->cause < 0` 是一个非常巧妙的实现。因为 `intptr_t` 是一个有符号整型，当 `scause` 的最高位为1时，它在有符号数中表示一个负数，所以这个条件就成立了，进而调用 `interrupt_handler`。反之，如果最高位为0（正数），则调用 `exception_handler`。

### 3. RISC-V特权级别分别是什么？

RISC-V 定义了三个核心的特权级别，从高到低分别是：

1.  **M 模式 (Machine Mode)**：机器模式，是 RISC-V 处理器中**最高**的特权级。它拥有对所有硬件资源的完全访问权限，包括物理内存、I/O 和所有控制状态寄存器（CSRs）。处理器启动时就处于 M 模式。通常，底层的固件（如本实验中的 OpenSBI）运行在 M 模式。

2.  **S 模式 (Supervisor Mode)**：监管者模式，是为现代操作系统内核设计的特权级。它支持虚拟内存管理（通过页表），并可以处理大部分来自用户程序的陷阱。我们的 ucore 内核就运行在 S 模式。

3.  **U 模式 (User Mode)**：用户模式，是**最低**的特权级。用户应用程序运行在此模式下，其对硬件的访问受到严格限制。如果用户程序需要访问系统资源（如文件、网络），必须通过 `ecall` 指令发起系统调用，陷入（trap）到 S 模式，由操作系统内核代为完成。

### 4. 哪些特权可以触发trap？

**所有特权级别（M/S/U）都可以触发trap**。Trap 是处理器执行流程中一种正常的（或异常的）控制转移机制，它可以在任何模式下发生。

*   **在 U 模式**：最常见的情况。应用程序执行 `ecall` 进行系统调用，或者发生缺页、非法指令等异常，都会触发 trap，通常会陷入到 S 模式。
*   **在 S 模式**：内核自身也可能触发 trap。例如，当时钟中断发生时，内核代码的执行会被打断，这是一种 S 模式下的 trap（自陷）。内核也可能主动执行 `ecall`，向 M 模式的固件请求服务（如设置定时器）。
*   **在 M 模式**：M 模式也可能遇到 trap，例如处理一些不可被委托给 S 模式的严重硬件错误。

### 5. 解释上下文切换

**上下文（Context）** 指的是处理器在某个特定时刻的完整状态，主要包括：
*   **通用寄存器** (`x0`-`x31`) 的值。
*   **程序计数器（PC）** 的值，即下一条要执行的指令地址。
*   **特权级相关的控制状态寄存器（CSRs）** 的值，如 `sstatus`, `sepc` 等。

**上下文切换（Context Switch）** 就是**保存当前正在执行流的上下文，并加载另一个执行流的上下文**的过程。

在本次实验的场景中，当中断发生时：
1.  **保存上下文**：处理器正在执行的程序被打断。为了能在中断处理结束后回来继续执行，必须把它被打断时的所有状态（即上下文）保存起来。在 ucore 中，`trapentry.S` 中的 `SAVE_ALL` 宏负责将32个通用寄存器和 `sstatus`, `sepc`, `scause` 等 CSR 的值压入内核栈中，形成一个 `trapframe` 结构体。
2.  **加载新上下文**：切换到中断处理程序的上下文。在这个实验里，中断处理程序在内核中，它会使用内核的栈和寄存器。`move a0, sp` 这条指令就是将指向 `trapframe` 的栈指针作为参数，传递给 C 语言实现的 `trap` 函数。
3.  **恢复上下文**：中断处理结束后，`RESTORE_ALL` 宏负责从栈上的 `trapframe` 中，将之前保存的值弹回到各个寄存器中。
4.  执行 `sret` 指令，处理器会根据恢复的 `sepc` 和 `sstatus` 等寄存器的值，精确地回到被打断的地方，恢复执行。

这个过程保证了中断处理对被中断的程序来说是“透明”的。

### 6. 为什么要屏蔽中断，什么场景屏蔽中断？

**屏蔽中断**（或称关闭中断、禁用中断）是为了保证一段代码的**原子性（Atomicity）**。原子操作指的是一个不可被中途打断的操作序列，它要么全部执行完毕，要么完全不执行。

**为什么要屏蔽中断？**
如果在一个关键操作执行到一半时，一个中断到来了，CPU 会转去执行中断服务程序。如果这个中断服务程序也可能修改同样的数据，或者依赖于这个数据处于一个稳定状态，那么就会导致数据不一致、竞争条件（Race Condition）甚至系统崩溃。

**什么场景需要屏蔽中断？**
通常是在**修改全局的、被中断服务程序和内核其他部分共享的关键数据结构**时。
*   **内存管理**：实验指导书中给出了一个绝佳的例子。在 `alloc_pages` 或 `free_pages` 函数中，需要修改物理内存的空闲链表。如果在修改链表指针的过程中（比如，刚断开一个节点，还没接上新的节点），一个中断发生，并且中断服务程序也尝试申请或释放内存，它会看到一个被破坏的、不完整的链表，这几乎必然导致系统崩溃。因此，在修改前必须用 `local_intr_save` 关闭中断，修改完成后再用 `local_intr_restore` 恢复中断状态。
*   **进程/线程调度**：在修改进程控制块（PCB）状态或操作调度队列时。
*   **中断处理入口**：在保存上下文的极短时间内，不希望被新的中断再次打断，以防状态保存不完整。RISC-V 硬件在进入 trap 时会自动禁用中断，这是一个硬件层面的保障。

### 7. 委托到S模式后，如何找到对应处理程序？

当中断或异常被 M 模式的固件（OpenSBI）委托给 S 模式后，处理器需要知道应该跳转到哪里去执行 S 模式的陷阱处理代码。这个过程分为两步：

1.  **硬件定位入口**：
    *   RISC-V 架构提供了一个名为 `stvec`（Supervisor Trap Vector Base Address Register）的 CSR。
    *   这个寄存器里存储着 S 模式下所有陷阱的**统一入口地址**。
    *   在操作系统初始化阶段（ucore 的 `idt_init` 函数），内核会把它的陷阱处理入口函数（即 `trapentry.S` 中的 `__alltraps` 标签地址）写入到 `stvec` 寄存器中。
    *   当一个被委托到 S 模式的 trap 发生时，RISC-V 硬件会自动地、无条件地将程序计数器（PC）设置为 `stvec` 中存储的地址，从而跳转到 `__alltraps` 开始执行。

2.  **软件分发处理**：
    *   硬件只负责跳转到 `__alltraps` 这个统一的入口。但具体是哪种中断（时钟？外部设备？）或哪种异常（缺页？非法指令？），硬件不负责区分。
    *   这个区分的工作由软件完成。在 `__alltraps` 保存完上下文后，会调用 C 函数 `trap`，并最终进入 `trap_dispatch`。
    *   `trap_dispatch` 函数会读取 `scause` 寄存器保存的值，通过这个值来判断陷阱的具体原因，然后调用相应的处理函数（如 `interrupt_handler` 或 `exception_handler`），在这些函数内部再通过 `switch-case` 语句分发到更具体的处理逻辑，例如时钟中断的处理代码。

总结一下，就是 **硬件通过 `stvec` 寄存器找到一个总的入口，然后软件通过 `scause` 寄存器的值进行二次分发，找到精确的处理程序**。
